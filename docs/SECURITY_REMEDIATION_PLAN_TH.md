## เข้าใจภาพรวมก่อน (ELI10)

ระบบนี้เหมือน **ร้านที่ประตูไม่ได้ล็อก และมีสมุดรหัสผ่านพนักงานวางอยู่บนเคาน์เตอร์**

- ประตูไม่ล็อก = ฐานข้อมูลเปิดให้ใครก็เข้าถึงได้
- สมุดรหัสผ่าน = รหัสพนักงานเก็บเป็นข้อความอ่านออก
- กุญแจสำรองแขวนหน้าร้าน = token / API key อยู่ในโค้ดที่คนนอกเห็นได้

ข่าวดี: **กลอนประตูทำไว้แล้ว** (ไฟล์ `database.rules.json` เขียนเสร็จ) แค่ยังไม่ได้ติดตั้ง

### P1-1 · Telegram Bot Token หลุดใน GitHub สาธารณะ

**หลักฐาน:** ไฟล์ `.env` ถูก commit ใน `40a9afb` ทั้งที่มีชื่ออยู่ใน `.gitignore` แล้ว
สาเหตุ: `.gitignore` **ไม่มีผลกับไฟล์ที่ถูก track ไปแล้ว** ต้องสั่ง `git rm --cached` เพิ่ม

**ทดสอบยืนยัน:** repo `neoKP/subcontractor-truck-management-system` ตอบ HTTP 200 โดยไม่ต้อง login → เป็น public

**เสียหายยังไง:** ใครก็ตามที่เปิด repo เจอ สามารถใช้ token ส่งข้อความปลอมเข้ากลุ่มบริษัท เช่น แจ้งงานปลอม หรือสั่งให้คนขับไปผิดที่

**วิธีแก้ (ตามลำดับ ห้ามสลับ):**

**⚠️ กับดักใหญ่ที่สุดของข้อนี้ — ย้ายไป Netlify env ไม่ได้แก้ปัญหา**

`utils/telegramNotify.ts:3` อ่านค่าผ่าน `import.meta.env.VITE_TELEGRAM_BOT_TOKEN` และ `utils/telegramNotify.ts:50` ยิง `fetch` ไปหา Telegram **จากเบราว์เซอร์ของผู้ใช้โดยตรง**

ตัวแปรที่ขึ้นต้นด้วย `VITE_` จะถูก Vite **ฝังลงในไฟล์ JS ตอน build** แปลว่า token จะอยู่ในไฟล์ที่ทุกคนดาวน์โหลดได้อยู่ดี ต่อให้ตั้งค่าใน Netlify ก็ตาม

> เปรียบเทียบ: เหมือนย้ายกุญแจจากใต้พรมไปแขวนไว้หน้าประตู — ยังเห็นอยู่ดี

**วิธีแก้ที่ถูกต้อง แบ่ง 2 ระยะ:**

**ระยะเร่งด่วน (วันนี้ ~20 นาที) — ลดความเสียหาย**

1. เปิด Telegram แชทกับ `@BotFather` → `/revoke` → เลือกบอท → ได้ token ใหม่
2. **ยังไม่ต้องใส่ token ใหม่กลับเข้าโค้ด** (ถ้าใส่ ก็หลุดอีก) — ยอมให้การแจ้งเตือนเงียบชั่วคราว
3. เอา `.env` ออกจาก git: `git rm --cached .env`
4. แก้ `.env.example` ให้เหลือแต่ค่าตัวอย่าง (ตอนนี้มี Chat ID จริงอยู่)

**ระยะถัดไป (~3-4 ชม.) — แก้ที่ต้นเหตุ**

5. ย้ายการส่ง Telegram ไปไว้ใน Cloud Function (มี `functions/` อยู่แล้ว) ให้ token อยู่ฝั่งเซิร์ฟเวอร์
6. หน้าเว็บเรียก Function แทนการยิง Telegram ตรง ๆ
7. ตั้ง token ใหม่เป็น secret ของ Function ไม่ใช่ `VITE_` env

> **สำคัญ:** ต้องยกเลิก token เดิมก่อนเสมอ — การลบไฟล์ออกจาก git ไม่ได้ทำให้ token เก่าใช้ไม่ได้ เพราะมันยังอยู่ใน git history และคนที่ clone ไปแล้วยังมีอยู่

**ความเสี่ยง:** ต่ำ · ระหว่างรอระยะถัดไป การแจ้งเตือน Telegram จะไม่ทำงาน (ยอมรับได้ เพราะดีกว่าปล่อย token หลุด)

### P1-2 · ฐานข้อมูลเปิดให้ใครก็อ่าน/เขียนได้

**หลักฐาน:** ยิง REST ทดสอบจริงได้ `HTTP 200` — อ่านข้อมูลได้โดยไม่ต้อง login

**เสียหายยังไง:** ข้อมูลลูกค้า ราคา ต้นทุน กำไร และ **รหัสผ่านพนักงานทุกคน** เปิดให้อ่านได้จากเบราว์เซอร์ธรรมดา และเขียนทับได้ด้วย

**ข่าวดี:** ไฟล์ `database.rules.json` เขียนกลอนไว้เรียบร้อยแล้ว รอแค่ติดตั้ง

**⚠️ กับดักที่ต้องระวัง 2 ข้อ:**

**กับดัก 1 — ลำดับสำคัญมาก**
`firebaseConfig.ts` เรียก `signInAnonymously()` ไว้แล้ว แต่ถ้ายังไม่เปิด Anonymous provider ใน Firebase Console การ sign-in จะล้มเหลวเงียบ ๆ
→ ถ้า deploy rules ตอนนี้เลย **ทุกคนใช้งานไม่ได้ทันที**

**กับดัก 2 — คำสั่ง deploy ที่จดไว้ใช้ไม่ได้**
คอมเมนต์ในไฟล์เขียนว่าให้ใช้ `firebase deploy --only database` แต่ `firebase.json` **ไม่มีการชี้ไปที่ไฟล์ rules เลย** ต้องเพิ่มก่อน:

```json
"database": { "rules": "database.rules.json" }
```

**กับดัก 3 — `authReady` ประกาศไว้แต่ไม่มีใครเรียกใช้**
`firebaseConfig.ts:34` สร้าง `authReady` ไว้แล้ว แต่ค้นทั้งโปรเจกต์**ไม่มีไฟล์ไหน `await` มันเลย**
แปลว่าตอนเปิดเว็บ โค้ดอาจอ่าน `/users` **ก่อน** sign-in เสร็จ → หน้า login ไม่มีรายชื่อผู้ใช้ → **ล็อกทุกคนออกจากระบบ**
→ ต้องแก้โค้ดให้ `await authReady` ก่อนอ่าน/เขียนครั้งแรก **ก่อน** deploy rules

**ขั้นตอนที่ถูกต้อง:**

1. Firebase Console → Authentication → Sign-in method → เปิด **Anonymous**
2. เปิดเว็บระบบ กด F12 ดู Console — ต้อง**ไม่มี**ข้อความ `Anonymous sign-in failed`
3. **แก้โค้ดให้ `await authReady` ก่อนอ่าน/เขียน Firebase ครั้งแรก** (กับดัก 3)
4. เพิ่ม `"database"` ใน `firebase.json` (โค้ดข้างบน)
5. `firebase deploy --only database`
6. ทดสอบ: ยิง REST อีกครั้ง ต้องได้ **401** ไม่ใช่ 200
7. ทดสอบใช้งานจริง: login → สร้างงาน → แก้งาน ต้องทำได้ปกติ

---

#### ⚠️ ข้อจำกัดที่ต้องเข้าใจ — ขั้นนี้ยัง "ไม่ปลอดภัยจริง"

Rules ที่เขียนไว้ใช้เงื่อนไข `auth != null` ซึ่งแปลว่า **"ขอแค่ล็อกอินอะไรก็ได้"** และ Anonymous auth คือการที่**ใครก็ขอบัตรผ่านได้ฟรีจากหน้าเว็บ**

เปรียบเทียบ: เหมือนติดกลอนประตูแล้วแขวนกุญแจไว้ข้างประตูให้ใครหยิบก็ได้ — กันคนเดินผ่านได้ แต่กันคนตั้งใจไม่ได้

**สิ่งที่ขั้นนี้กันได้จริง:** การยิง REST ตรง ๆ จากคนที่ไม่ได้ตั้งใจเจาะ (สแกนเนอร์อัตโนมัติ, คนที่บังเอิญเจอ URL)

**สิ่งที่ยังกันไม่ได้:** คนที่เปิดโค้ดหน้าเว็บดู แล้วขอ anonymous token เองแล้วอ่าน/เขียนทั้งฐานข้อมูล

**ปลอดภัยจริงต้องทำถึงระยะที่ 4** (Firebase Auth จริง + rules ที่อ้าง `auth.uid` และ role จากฝั่งเซิร์ฟเวอร์)

ถึงอย่างนั้น **ยังควรทำขั้นนี้ก่อน** เพราะใช้เวลา 30 นาที ลดความเสี่ยงเฉพาะหน้าได้ทันที และเป็นบันไดขั้นแรกของระยะที่ 4

**Rollback (ใช้เมื่อจำเป็นจริงเท่านั้น):** ถ้าระบบล่ม → แก้ `database.rules.json` ให้ `.read`/`.write` เป็น `true` แล้ว deploy ซ้ำ (~1 นาที)

> 🚨 **ระวัง:** นี่คือการ**เปิดฐานข้อมูลให้ทุกคนอีกครั้ง** ซึ่งคือปัญหา P1-2 ที่กำลังแก้อยู่พอดี ถ้าลืมปิดกลับ = กลับไปจุดเดิมโดยไม่รู้ตัว
>
> **ถ้าต้องใช้ rollback นี้ ให้ทำ 2 อย่างทันที:**
> 1. ตั้งเตือนในมือถือ/ปฏิทินว่าต้องกลับมาแก้ (อย่าอาศัยความจำ)
> 2. หาสาเหตุแล้ว deploy rules กลับให้เร็วที่สุดในวันเดียวกัน
>
> ทางที่ปลอดภัยกว่า: **ทดสอบในเวลาที่คนใช้งานน้อย** (เช่น หลังเลิกงาน) จะได้มีเวลาแก้โดยไม่ต้อง rollback

**เวลาที่ใช้:** ~30 นาที · **ความเสี่ยง:** สูงถ้าข้ามขั้น / ต่ำถ้าทำตามลำดับ

### P1-3 · Race condition — ข้อมูลหายเมื่อสองคนทำงานพร้อมกัน

**หลักฐาน:** `App.tsx:345`, `App.tsx:392`, `App.tsx:417` ใช้ `set()` เขียนทับ**ทั้งงาน**จากข้อมูลเก่าที่ค้างในหน้าจอ

**เสียหายยังไง (สถานการณ์จริง):**

```
09:50  บัญชีเปิดหน้าตรวจงาน (ข้อมูลค้างในจอตั้งแต่ตอนนี้)
10:00  พนักงานหน้างานอัปโหลดรูป POD  → บันทึกสำเร็จ
10:01  บัญชีกดอนุมัติ → set() เขียนทับด้วยข้อมูล 09:50
       → รูป POD หายทันที ไม่มีทางกู้
```

**วิธีแก้:** เปลี่ยนจาก `set()` (เขียนทับทั้งก้อน) เป็น `update()` (แก้เฉพาะช่องที่เปลี่ยนจริง)

เปรียบเทียบ: `set()` = ฉีกกระดาษทั้งแผ่นแล้วเขียนใหม่ · `update()` = ลบยางเฉพาะบรรทัดที่จะแก้

**ขอบเขต — นับจากของจริงแล้ว:** ทั้งโปรเจกต์มี `set(ref(db, ...))` รวม 16 จุด แต่**ที่เป็นปัญหาจริงมีแค่ 3 จุด** คือจุดที่เขียนทับ `jobs/${id}` ทั้งก้อน

จุดอื่นไม่ต้องแก้ เพราะเป็นการ**สร้างข้อมูลใหม่** (`invoices/`, `logs/`, `subcontractorMasters/`) หรือเป็น seed ผู้ใช้ตอนเปิดระบบ — `set()` ถูกต้องแล้วสำหรับกรณีเหล่านี้

> ข้อยกเว้นที่ต้องดูเพิ่ม: `App.tsx:470` เขียนทับ `priceMatrix` **ทั้งตาราง** ในครั้งเดียว ถ้าสองคนแก้ตารางราคาพร้อมกัน ของอีกคนจะหายทั้งหมด ควรแก้ด้วยแต่แยกเป็นงานต่างหาก

**เวลาที่ใช้:** ~2 ชั่วโมง (ลดลงจากที่ประเมินไว้ เพราะขอบเขตเล็กกว่าที่คิด) · **ความเสี่ยง:** ปานกลาง ต้องทดสอบทุก flow

**Rollback:** `git revert` commit เดียวจบ (แนะนำแยก commit ต่อ 1 กลุ่มงาน)

### P1-4 · รหัสผ่านเป็นข้อความธรรมดา + ตรวจสอบที่ฝั่งเบราว์เซอร์

**หลักฐาน:**

- `App.tsx:35-47` — รายชื่อพนักงานจริง 13 คนพร้อมรหัสผ่าน
- `LoginPage.tsx:33` — `if (password === user.password)` เทียบที่ฝั่งเบราว์เซอร์
- `UserManagementView.tsx:264` — แสดงรหัสผ่านทุกคนบนหน้าจอ

**เสียหายยังไง:** รวมกับ P1-2 = ใครก็ได้ดึงรหัสแอดมินไปใช้ ต่อให้ปิด P1-2 แล้ว ผู้ใช้ที่ login ได้คนเดียวก็ยังอ่านรหัสของทุกคนได้ รวมถึงแอดมิน

**ทำไมไม่แก้ทันที:** ต้องรื้อระบบ login ทั้งหมด เป็นงานใหญ่ที่กระทบผู้ใช้ทุกคน ควรวางแผนแยก

**ทางเลือก:**

| แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| **A. Firebase Auth เต็มรูปแบบ** (แนะนำ) | มาตรฐาน ปลอดภัยสูงสุด rules อ้าง uid ได้ | ต้องย้ายผู้ใช้ทั้งหมด ~2-3 วัน |
| **B. hash รหัสผ่าน + login ผ่าน Cloud Function** | เร็วกว่า ใช้ `functions/` ที่มีอยู่แล้ว | ยังไม่ได้มาตรฐานเต็ม ~1 วัน |
| **C. แก้เฉพาะไม่ให้แสดงรหัสบนหน้าจอ** | 10 นาที | แก้แค่อาการ ต้นเหตุยังอยู่ |

**แนะนำ:** ทำ **C ทันที** (ลดความเสี่ยงเฉพาะหน้า) แล้ววางแผน **A** ต่อ

### P1-5 · ปลอมสิทธิ์ได้จากเบราว์เซอร์ (localStorage)

**หลักฐาน:** `App.tsx:496` และ `App.tsx:511` เก็บข้อมูลผู้ใช้ที่ล็อกอิน **รวมถึง role** ไว้ใน `localStorage` แล้วอ่านกลับมาใช้ตอนเปิดเว็บ

**เสียหายยังไง:** ผู้ใช้ทั่วไป (เช่น พนักงานหน้างาน) เปิด devtools แก้ค่า `currentUser` ใน localStorage ให้ `role` เป็น `ADMIN` แล้วรีเฟรช → ได้สิทธิ์แอดมินทันที เข้าหน้าอนุมัติเงิน/จัดการผู้ใช้ได้

**ทำไมเรื่องนี้สำคัญกว่าที่คิด:** ทำให้การ "ใส่ role guard" (P2-3) **ไม่ใช่การป้องกันจริง** — เป็นแค่การซ่อนเมนู เพราะ role ที่เอามาเช็คนั้นผู้ใช้แก้เองได้

**วิธีแก้:** ต้องให้ฝั่งเซิร์ฟเวอร์เป็นคนบอก role — ทำได้จริงเมื่อย้ายไป Firebase Auth (ระยะที่ 4) แล้วใช้ custom claims + rules ที่อ้าง `auth.uid`

> สรุป: role guard ยังควรใส่ (กันการกดพลาด/เข้าหน้าผิด) แต่**อย่าเข้าใจผิดว่ามันคือความปลอดภัย** ความปลอดภัยจริงมาตอนระยะที่ 4

### P1-6 · NAS API Key ฝังในโค้ดหน้าบ้าน + endpoint เปิดกว้าง

**หลักฐาน:** `utils/nasUpload.ts:4` — คีย์ถูกรวมเข้าไฟล์ JS ที่ส่งให้ทุกเบราว์เซอร์

**เสียหายยังไง:** ใครก็ได้อัปโหลดไฟล์เข้า NAS บริษัท (มัลแวร์ ไฟล์ขยะจนเต็มดิสก์)

**ปัญหาซ้อนที่เจอเพิ่ม (ตรวจไฟล์ PHP แล้ว):**

1. **CORS เปิดหมด** — `nas-api/upload.php:25`, `serve.php:14`, `proxy-download.php:12`, `diag.php:5` ตั้ง `Access-Control-Allow-Origin: *` แปลว่าเว็บไซต์ใดก็เรียก API นี้ได้
2. **โหมด proxy_download รับ URL อะไรก็ได้** — `upload.php:50-58` ดาวน์โหลดจาก URL ที่ผู้เรียกส่งมา **และปิดการตรวจใบรับรอง SSL** (`verify_peer => false`)
   → คนนอกใช้ NAS ของบริษัทเป็นตัวกลางยิงไปยังเครื่องอื่นในวงแลนได้ (เรียกว่า SSRF)

**รวมกับคีย์ที่หลุดในโค้ดหน้าบ้าน = ใครก็สั่ง NAS ทำงานแทนตัวเองได้**

**วิธีแก้:** ย้ายการอัปโหลดไปผ่าน Cloud Function (มี `functions/` อยู่แล้ว) ให้คีย์อยู่ฝั่งเซิร์ฟเวอร์เท่านั้น

**แก้ชั่วคราวได้ทันที (~1 ชม.):**

> ⚠️ **CORS ไม่ใช่การป้องกันหลัก** — มันกันแค่เว็บไซต์อื่นที่เรียกผ่านเบราว์เซอร์ แต่**ไม่กัน** คนที่ยิงตรงด้วย `curl` หรือสคริปต์ ตัวที่กันจริงคือการตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์ + เปลี่ยนคีย์ใหม่

- **เปลี่ยนคีย์ NAS ใหม่** (คีย์เดิมหลุดในโค้ดหน้าเว็บแล้ว ถือว่าใช้ไม่ได้อีกต่อไป — ดู P1-8)
- เปลี่ยน `Access-Control-Allow-Origin` จาก `*` เป็นโดเมนของระบบเท่านั้น
- ปิดหรือจำกัดโหมด `proxy_download` ให้รับเฉพาะโดเมนที่อนุญาต (allowlist)
- เปิด `verify_peer` กลับเป็น `true`
- จำกัดชนิด/ขนาดไฟล์ที่อัปโหลดได้

### P1-7 · ไฟล์ PHP บน NAS ที่สั่งงานระบบได้โดยไม่ต้องยืนยันตัวตน

**นี่คือข้อที่อันตรายที่สุดในเอกสารนี้** เพราะเปิด URL อย่างเดียวก็สั่งงานเซิร์ฟเวอร์ได้

| ไฟล์ | ทำอะไรได้ | มีการตรวจสิทธิ์ไหม |
|---|---|---|
| `nas-api/fix-perms.php` | สั่ง `chmod 777` และ `ls` ระบบไฟล์ผ่าน `shell_exec` | ❌ **ไม่มีเลย** |
| `nas-api/list-files.php` | ดูรายการไฟล์ทั้งหมดบน NAS | ❌ **ไม่มีเลย** |
| `nas-api/copy-to-drive.php` | รัน `mkdir` / `cp` / `sudo` ผ่าน shell | ⚠️ มี แต่ส่งคีย์ทาง URL (`?key=...`) จึงติดใน log/history |

**เสียหายยังไง:** `chmod 777` แปลว่า "ให้ทุกคนอ่าน เขียน ลบ ไฟล์นี้ได้" ใครก็เปิด `fix-perms.php` แล้วเปิดสิทธิ์โฟลเดอร์ทิ้งไว้ จากนั้นใช้ `list-files.php` ดูว่ามีอะไรบ้าง แล้วอัปโหลดไฟล์อันตรายเข้าไปได้

> ในไฟล์ `fix-perms.php` บรรทัดที่ 2 เขียนคอมเมนต์ไว้เองว่า **"ลบไฟล์นี้ทิ้งหลังใช้งาน!"** — แต่ยังอยู่

**วิธีแก้ (ทำได้ทันที ~10 นาที):**

1. **ลบ `fix-perms.php` ออกจาก NAS ทันที** (เป็นไฟล์ debug ที่ไม่ควรอยู่บนเครื่องจริง)
2. ลบหรือใส่การตรวจสิทธิ์ให้ `list-files.php` และ `copy-to-drive.php`
3. เปลี่ยนการส่งคีย์จาก URL (`?key=`) เป็น HTTP header
